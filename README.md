# claude-config

Portable Claude Code configuration that travels between machines. This repo is
**a plugin marketplace, a small dotfiles install, and a home for reusable GitHub
workflows**, because each reaches a repo by a different route.

Everything here is **project-agnostic** — nothing is tied to a particular
employer, forge, or issue tracker — and **no secrets are tracked**.

## The two halves

| Half | Ships as | Why |
| --- | --- | --- |
| Skills, commands, hooks, mods | **Plugins** (7) | Plugins are the supported mechanism: versioned, per-profile toggles, `/plugin update`, namespaced, and installing one never touches your existing skills |
| Global rules, settings, keybindings | **Symlinks** via `install.sh` | Plugins cannot provide always-loaded `CLAUDE.md` instructions, `paths:`-scoped `rules/*.md`, or `settings.json` |

## Install on a new machine

```sh
git clone git@github.com:yaniv120892/claude-config.git ~/Develop/claude-config
cd ~/Develop/claude-config

# Half 1 — rules, settings, keybindings
./install.sh --dry-run      # see exactly what would change
./install.sh                # personal profile → ~/.claude

# Half 2 — skills, commands, hooks, mods
claude
/plugin marketplace add yaniv120892/claude-config
/plugin install pr-workflows@yaniv-claude-config
/plugin install dev-workflows@yaniv-claude-config
/plugin install issue-tracker@yaniv-claude-config
/plugin install infra-workflows@yaniv-claude-config
/plugin install mods@yaniv-claude-config
/plugin install cockpit@yaniv-claude-config
/plugin install cmux@yaniv-claude-config
```

`install.sh` symlinks, so editing a file here takes effect immediately and
`git status` is the single source of truth for what you've changed. The exception
is `settings.json`, which is copied rather than linked, because Claude Code
writes machine-local state into it. Re-running `install.sh` adds each top-level
key the repo's copy has and yours lacks, and never overwrites one you have. Anything replaced is moved to
`~/.claude-config-backups/<timestamp>/` first.

Add `--profile work` or `--target ~/.claude-personal` for a second profile.

### On Codex

```sh
./install.sh --harness codex   # or --harness all for both
```

Every skill is linked into `~/.agents/skills/`, where Codex discovers skills.
`$CODEX_HOME/AGENTS.md` (default `~/.codex/AGENTS.md`) is generated by
`scripts/agents_md.py` from the profile's `CLAUDE.md`. Codex follows no `@`
imports and has no `paths:` scoping, so the imports are inlined, the path-scoped
rules become an index to read on demand, and a closing table says what the skills'
Claude-specific terms mean (`${CLAUDE_PLUGIN_ROOT}`, `Agent(...)`,
`AskUserQuestion`). Re-run the installer after editing a rule; the skills are
links and need nothing. An `AGENTS.md` you wrote yourself is backed up, not
overwritten.

A skill marked `disable-model-invocation: true` also carries an
`agents/openai.yaml` with `allow_implicit_invocation: false`, the key Codex reads
instead; `tests/test_codex_policy.py` keeps the two in step.

What does not carry over: the hooks (the pre-push quality gate, the worktree
guard), the mods (the default-branch guard, the secret
guard, the status band), `settings.json`, and keybindings. The generated `AGENTS.md` asks the agent to keep the rules the hooks
enforce, but nothing on Codex enforces them.

## The plugins

| Plugin | Skills | What it does |
| --- | --- | --- |
| `pr-workflows` | 15 | GitHub pull request workflow: create, review (house rules plus a Fowler smell baseline, batched across PRs with a Notion docs-drift check), inline comments, CI verification, thread resolution, conflict fixing, the `steward` drive-to-green posture, feedback harvesting, posting a PR to Slack. Ships `/pr-review` and `lib/github.py` |
| `dev-workflows` | 14 | Docker-based service runs, drip-feed recurring maintenance, domain modeling (`CONTEXT.md` + ADRs), the `/flows` router, `investigate-alert` (is an alert new, which deploy it follows, is it my latest PR), and the `wizard`/`research`/`retro`/`wait-what` helpers. Ships the pre-push quality-gate, post-merge cleanup and require-worktree hooks |
| `issue-tracker` | 3 | Jira ticket creation and status transitions, with a cached per-project transition map. Also files Linear issues against a fixed Why/Repro/Fix/Done-when/Signals template |
| `infra-workflows` | 2 | Helm env vars across GitOps registries, and AWS SSM SecureString provisioning with an account guard. Ships `provision_ssm.sh` |
| `mods` | 0 | Function-hook mods for the harness itself: the default-branch guard, the status band, `/pr`, the secret guard, the reply-style rule and `/skill-tally` — see *Mods* below |
| `cockpit` | 0 | A `/cockpit` pane for the work around the code: the Slack PR inbox, your PRs and Linear tickets, deploy alerts, skill buttons, a Compact button and a usage line — see *Cockpit* below |
| `cmux` | 5 | cmux terminal multiplexer control: topology, workspaces, browser surface, notifications |

Plugins that touch an employer's systems read their site-specific values — accounts,
project keys, Slack channels, repo paths — from a machine-local
`~/.claude/<plugin>.config.json`. Each ships a `config.example.json` showing the shape,
and never the values. Moving to a new employer is a config swap, not a skill rewrite.

Enable or disable a whole plugin per profile through `enabledPlugins` in
`settings.json` — that replaces maintaining a `skillOverrides` list of individual
skill names.

### One CLI, no tokens in scripts

The PR skills drive `gh` and nothing else. Their scripts share `lib/github.py`,
which owns the parts worth writing once — inline-comment position payloads,
thread resolution (GraphQL, since REST cannot express it), merge-base resolution
— and routes every API call through `gh api` so **no script ever reads a token**.

```sh
# smoke-test the layer from inside any repo
python3 ~/.claude/plugins/.../pr-workflows/lib/github.py
# → repo=owner/name
```

Scripts resolve `${CLAUDE_PLUGIN_ROOT}` when installed and fall back to walking up
to the plugin root when run straight from a clone, so both work.

### Mods

`mods` is a plugin of function hooks: one TypeScript module,
`plugins/mods/hooks/register.tsx`, that Claude Code loads into the session and
calls on its own events. Each mod has a switch in `/config`, and all start on.

| Mod | What it does | What it replaced |
| --- | --- | --- |
| Default-branch guard | Refuses `git commit` and `git push` whose target checkout is on the default branch (`origin/HEAD`, else `main` or `master`). The target is followed through the command: each `cd`, a `-C`, and the variables the command assigns; a path it cannot read off the text is let through rather than guessed. A push that only deletes other branches (`--delete`, `-d` or `:branch`) goes through. `ALLOW_DEFAULT_BRANCH_WRITE=1` before the git command opts out | dev-workflows' `protect-default-branch.sh`, which resolved only the last `cd` and no variables, so it blocked writes in worktrees |
| Status band | Above the prompt, in the terminal and the desktop app: `➜  repo/dir git:(branch) ✗ [model] ctx 30% ⇣280k · 5h 58% ↻2h · wk 7% ↻6d` — the context as a share of the auto-compact threshold, so 100% is when it compacts, with the tokens left before it does (the share of the window when auto-compact is off), counted from the last API response as the cockpit's usage line counts it; the 5-hour and weekly usage limits, shown on a subscription, each with the time to its reset; off a subscription, the session's cost (`$1.24`) in their place — then a row for the branch's PR and one for each PR opened this session (up to three; found from what `gh pr create` prints and from `gh pr list --author @me` since the session began, so a PR a subagent or another worktree opened shows too): who is on it (assignees, requested reviewers and reviewers, each by the emoji the `peopleMarks` option gives their login, else `@login`), where GitHub stands (`draft`, `awaiting review`, `approved`, `changes requested`, `merged`, `closed`), failing, pending and passing checks, review threads as `open` (waiting on you), `replied` (your reply was last) and `resolved`, conflicts or `behind base`, and `ready to merge` once GitHub's merge state is clean. The PRs are read through `gh` every 90 seconds, and again after a push, a `gh pr` write or a branch switch; a merged or closed one is not read again | `statusline-command.sh` and the `statusLine` setting |
| Plan progress | One band row under the location line while the main agent has a plan: `building · 2/5 tasks · Add retry tests`, from its `TodoWrite`, `TaskCreate` and `TaskUpdate` calls. The counts are the statuses the model declared, never a test result or an ETA; a deleted task leaves the count, a refused or failed call changes nothing, and a subagent's tasks never count. The title is cut to the band's width and dropped when it is narrow. Each session's plan is stored under its own id, so `claude --resume` brings it back, and is dropped a day after its last change | — |
| Alerts | A toast when the 5-hour or weekly limit passes 90%, once per window across sessions | — |
| `/pr` | A pane with the PR's checks (failing first), its unresolved threads by file and line, and buttons that start `address-pr-feedback`, `verify-pr-state` and `finalize-pr` | — |
| Secret guard | Refuses a Write, Edit or NotebookEdit that would put a credential (GitHub, AWS, Anthropic, OpenAI, Slack, Google, Linear, npm, a private key) in a file git tracks; a git-ignored file is fine. With `blockedTerms` set, it also refuses those terms in any repository with a `.claude-plugin/marketplace.json` | `rules/config.md` alone, which only loads when a config file is read |
| Reply style | Adds `prompts/reply-style.md` to the system prompt as its own section, so compaction cannot drop it | dev-workflows' SessionStart hook |
| PR skills | On each open PR's band row and in `/pr`: `✓simplify ○code-review ○pr-review ○prune`, whether `simplify`, `code-review`, `pr-review` and `prune-comments` (any plugin's) have run on it, in any session. A run counts for the PRs its arguments name (`65` or `#65`, resolved by `gh`; `owner/repo#65`; a PR link), read from the Skill call or the typed `/command`, once flags and effort levels are set aside; if anything else is left, or nothing is named, it counts for the branch the session is on. Runs other open sessions record show within 90 seconds. Never blocks, never resets | — |
| `/skill-tally` | Counts each skill that loads, across sessions, and lists the plugin skills that never did: the live half of what the trigger evals predict | — |
| Time awareness | Context the model reads and the person never sees: each prompt carries the local time (`Wed 2026-10-21 14:03 UTC+3`), and, when the session sat idle 30 minutes or more, how long, with a nudge to re-check state that may have moved (PRs, branches, deploys). Last activity is stored per session id, so a `claude --resume` days later counts. A tool call that ran 10 seconds or more is followed by `Bash took 47s to run.`, from the tool's own run time, permission prompts excluded | — |

### Cockpit

`cockpit` is a second plugin of function hooks. `/cockpit` opens one pane with
four tabs, each on a digit key, and a **Compact** button (no hotkey, so no
stray key compacts) that compacts the conversation. Under the tabs, on every
tab, one line shows the 5-hour and weekly limits with the time to their reset,
the context as a share of the auto-compact threshold with the tokens left before
it runs (`⇣98k to compact`), counted from the last API response as the status
band counts it, and the session's cost. While setup is unfinished, a line under
it says how many steps are left (`⚠ Setup: 2 steps left · press 3`):

| Tab | What it shows |
| --- | --- |
| Inbox | Every Slack message a person other than you posted that links a GitHub PR which is not your own (a bot's "PR opened" notice is left out): who, where, and **Claude**, **Codex** and **Dismiss** buttons, then 👀 ✅ 👍 reactions, **Reply** (a field that posts in the message's thread) and **Open in Slack**, each as you. Claude runs `/pr-workflows:pr-review <url>`, Codex runs `/pr-workflows:codex-pr-review <url>`. A new one raises a toast and a native notification once, and opens the pane (`openOnMessage`) |
| PRs | Your in-progress Linear tickets and the ones done in the last day, then every open PR you authored in any repository and the ones merged in the last day (a day on, a merged PR is in production): failing, pending and passing checks, review threads waiting on you and ones you answered, conflicts, the ticket its title or branch names, and `in prod 12m` once the merge commit's GitHub deployment to production succeeded. `▸` on a ticket lists its PRs. When the cmux workspace title names a ticket (`YAN-172 cockpit`), or else the branch does, only that ticket's PRs are listed, and **All PRs** shows the rest. Every open PR has **✦ Polish**, which runs `/pr-workflows:pr-polish` on it, and a PR that is green, free of conflicts, and approved or needing no review has **⇪ Merge** (a second press within 10 seconds confirms; it squash-merges through the API the head the board showed, so a later push makes it refuse, then deletes the branch unless it lives in a fork). A ticket whose PR merged while it stayed open shows `⚑ PR merged` and **✓ Move to Done**; an expanded ticket offers **⧉ Open a workspace for it** (`/cmux:ticket-workspace`). A toast says when one of your PRs fails CI, gets a new review thread, or turns ready to merge. A repo with no deployments shows a merged PR as merged, not as waiting for production. `▸` expands a PR to its failing checks and threads, each a link, with **Address feedback** and **Fix CI**; `✕` dismisses it on every session |
| Alerts | First, while any is left, the setup steps, each read from the options and from what Slack has shown, with what to do: the Slack tokens, the Slack link, reactions and replies allowed (done once one goes through; a `missing_scope` refusal asks for a reinstall), `alertChannels`, `eventChannels`, and an event in the last week. Then each message of the monitoring channels (`alertChannels`), with the same reactions, Reply and Open in Slack. One that arrives within `alertWindowMinutes` of a PR of yours reaching production is compared to that PR's title and files by a small model call and marked likely related, unclear or unlikely, with the reason; the first two notify you. Every alert has **🔎 Investigate**, which runs `dev-workflows:investigate-alert` on it |
| Skills | A button for each prompt in `pinnedSkills`, then the skills that load most |

GitHub is read through `gh` and Linear through the claude.ai Linear connector,
so neither needs a token here. Slack does.

**One reader per machine.** Every session on the machine shares one board
through the plugin's store. Each session looks at the stored board every 30
seconds and shows it when it is newer than its own; only when the board is due
does one session take a 60-second lease, read GitHub and Linear, store the
result and let the lease go. **Refresh**, `/cockpit`, a Merge, a Move to Done
and a Slack event read at once, unless another session holds the lease, whose
board then arrives on the next tick. The board is due every 2 minutes; every
10 when less than a fifth of the hour's GitHub GraphQL points are left (the PRs
footer says `slowed: GitHub quota 742/5000`) or when Slack events bring the
changes; and once GitHub refuses the query for its rate limit, at the reset.
Each session still toasts PR changes in its own terminal, from the board it
showed before.

**Slack events.** With `eventChannels` set, any message in those channels,
from a person or a bot, rereads the board 10 seconds after the burst it belongs
to, and the regular read slows to every 10 minutes as a fallback for missed
events. To feed one:

1. Create a private channel, such as `#cockpit-events`, and join it.
2. Add the GitHub Slack app to it and run
   `/github subscribe <owner/repo> pulls reviews comments` there for each repo
   you work in (`/github subscribe <owner>` covers an organization).
3. In Linear, connect the Slack integration and point your team's Slack
   channel notifications (team settings → *Slack notifications*) at that
   channel, so issue status changes post there.
4. `/config` → cockpit → *Event channels* → `cockpit-events`.

The app needs no new scope: `message.groups` and `message.channels` already
deliver the messages of channels you are in.

**Connecting Slack.** The mod listens through a Slack app in Socket Mode, on a
user token, so it sees what you see. A mod cannot hold a WebSocket, so
`plugins/cockpit/sidecar/slack-socket.mjs` (Node 22, no dependencies) holds it
and prints what matters to the mod. Each session starts one; a lock file
(`~/.claude/cockpit-slack.lock`) lets exactly one connect, since Slack hands
each event to a single connection, and another takes over when it exits. All
sessions share the inbox, the alerts and the dismissals.

1. <https://api.slack.com/apps> → *Create New App* → *From a manifest* → paste
   `plugins/cockpit/slack-app-manifest.yaml`. When the manifest gains a scope
   (reactions and replies need `reactions:write` and `chat:write`), paste it
   again under *App Manifest* and reinstall the app; save the `xoxp-` token
   again if Slack issues a new one.
2. *Basic Information* → *App-Level Tokens* → generate one with
   `connections:write`. That is the `xapp-` token.
3. *Install App* → install to the workspace. The *User OAuth Token* is the
   `xoxp-` token.
4. Save both in a terminal. The tokens are secret options, which `/config`
   does not list, and `read -s` keeps them off the screen and out of any chat:

   ```zsh
   read -s "XAPP?xapp token: "; echo; read -s "XOXP?xoxp token: "; echo
   XAPP=$XAPP XOXP=$XOXP node -e 'console.log(JSON.stringify({slackAppToken:process.env.XAPP,slackUserToken:process.env.XOXP}))' \
     | claude plugin configure cockpit@yaniv-claude-config --values-stdin
   ```

5. `/config` → cockpit → name the alert channels, and the event channels
   (*Slack events* above).

The Inbox tab's last line says where the connection stands.

Three limits to know. "In prod" is read from the GitHub deployments of the PR's
own merge commit, so a pipeline that deploys only the newest commit of a batch
leaves the earlier PRs at "merged, not in prod", and no alert is compared to
them. The toast and the native notification come from the one session that
holds the Slack connection; the others show the new row within 15 seconds,
silently. And in an alert channel only a top-level message someone else posted
counts as an alert: a reply in its thread is discussion.

The function-hook API is early access, so CI checks the mods on a pinned Claude
Code version (`.github/workflows/ci.yml`): `claude plugin validate`,
`claude plugin test` and `tsc`. Develop one with
`claude --plugin-dir plugins/mods`, which reloads the module on each save.
`cockpit` is checked the same way on the version it was written against, and
its sidecar with `node --test`. A
build of Claude Code older than function hooks loads none of this, the
default-branch guard included.

**Upgrading a machine that has the old pieces:** re-run `install.sh`. It removes
the links to the deleted scripts and names each entry of your kept
`settings.json` that still runs one, which you delete by hand.

## Skill evals

Each skill can carry `evals/evals.json`: prompts that should and shouldn't fire it,
and runs against a fixture repo with checks on the result. `evals/run.py` runs
them on Claude Code or Codex; `evals/README.md` covers how.

## Rules (the non-plugin half)

`shared-rules.md` loads on every prompt and holds only what is universal:
developer context, the rule-codification protocol, file-path convention,
conventional commits, and subagent conventions.

Everything else is **path-scoped** — each file in `rules/` has a `paths:`
frontmatter list and loads only when Claude reads a matching file, so a large
rule set costs nothing on unrelated prompts.

| File | Loads on | Covers |
| --- | --- | --- |
| `code.md` | ts, tsx, js, jsx, mjs, cjs, py, go, java, rb, sql, sh, bash | Language-agnostic craft: comments, naming, control flow, guards, error handling |
| `typescript.md` | ts, tsx | Typing, `as` casts, derived types, access modifiers, type placement |
| `python.md` | py | Type hints, Google docstrings, import order, tool-function error returns |
| `config.md` | env, tf, tfvars, settings.json, compose, values, CI yaml | Secret handling, environment-variable wiring |
| `migrations.md` | migrations directories, schema.prisma, sql | Expand/contract: every migration stays writable by the build still serving |
| `authoring-docs.md` | md, mdx | Writing rules, skills, and agent-facing docs: invariants over violation lists, positive phrasing, no-op pruning, leading words, pointer wording |

Verify what actually loaded in a session with `/context`.

## Layout

```
.claude-plugin/marketplace.json   the marketplace manifest
.github/workflows/                reusable workflows the app repos call
.github/actions/                  the composite actions those workflows use
tests/                            repo-wide checks, e.g. every plugin list matches the manifest
evals/run.py                      skill evals, run against Claude Code or Codex
plugins/<name>/                   one directory per plugin
  .claude-plugin/plugin.json      plugin manifest
  skills/<skill>/agents/openai.yaml  Codex invocation policy
  skills/ commands/ hooks/ lib/ references/
shared-rules.md                   → ~/.claude/shared-rules.md
rules/*.md                        → ~/.claude/rules/
rules-reference.md                → ~/.claude/rules-reference.md
profiles/<name>/CLAUDE.md         → <profile>/CLAUDE.md
settings/settings.json            → <profile>/settings.json (copied)
keybindings.json
install.sh                        installs the non-plugin half, or the Codex setup
scripts/agents_md.py              builds the Codex AGENTS.md from the profile
```

## Two profiles

Claude Code picks its config directory from `CLAUDE_CONFIG_DIR`:

```sh
alias claude-work='CLAUDE_CONFIG_DIR=~/.claude claude'
alias claude-personal='CLAUDE_CONFIG_DIR=~/.claude-personal claude'
```

Both profiles share `shared-rules.md`, `rules/`, and `rules-reference.md`, which
always install under `~/.claude` because `CLAUDE.md` imports them by absolute path
(`@~/.claude/shared-rules.md`). Only `CLAUDE.md`, `keybindings.json`, and
`settings.json` are profile-scoped — plus whichever plugins each profile enables.

The work profile carries no employer details. `profiles/work/CLAUDE.md` imports
`~/.claude/work-context.local.md`, which this repo never tracks — put the real
email, issue-key prefix, and repo names there. Without it the profile still
installs and reads as placeholders, so the repo stays publishable and a fresh
machine is one file away from being fully configured.

## Secrets

**Nothing secret is tracked here, and nothing secret should ever be added.**
`.mcp.json`, `settings.local.json`, and `.env*` are gitignored.

Put credentials in your shell profile and reference them:

```sh
# ~/.zshrc — not tracked
export ATLASSIAN_API_TOKEN="..."
```

Claude Code expands `${VAR}` inside `.mcp.json`, so a server config can reference
an env var without the value landing in a file. See `mcp/mcp.json.example`.

If a secret ever does get committed, rotate it — deleting the line is not enough.

## Adding things

**A skill, command, or hook** → the matching plugin under `plugins/`, then bump
that plugin's `version` in its `plugin.json` so `/plugin update` picks it up.

**A rule** → decide scope first, per the protocol in `shared-rules.md`:
every session → `shared-rules.md`, or a section the `mods` plugin adds to the
system prompt when it must also reach cloud sessions, which load no
`shared-rules.md` (`plugins/mods/prompts/reply-style.md` is the example); a language or file type → `rules/*.md` (needs
`paths:`); one project → that repo's `.claude/rules/`. Add the long-form version
with worked examples to `rules-reference.md` either way.
